This quickstart walks through the MVP layout a team would need.

The example models a common enterprise case: platform engineering owns standard SDLC skill prose, while the payments team overrides the testing guidance without weakening locked security and run-record blocks.

## 1. Define The Base

The base is a structured envelope around Markdown.

This is the smallest useful abstraction: enough structure for Kustomize patches and policy checks, but no new skill runtime model.

```yaml
# /skills/sdlc/base/skill.yaml
apiVersion: skills.agent.dev/v1alpha1
kind: Skill
metadata:
  name: enterprise-sdlc
spec:
  description: Enterprise SDLC guidance for agentic code changes.
  target: SKILL.md
  contract:
    lockedBlocks:
      - security-review
      - run-record
    allowedPatchPaths:
      - /spec/blocks/2/markdown
    allowedCommandPatterns:
      - npm test
      - make test-*
  blocks:
    - id: purpose
      markdown: |
        # Enterprise SDLC

        Use this skill when making code changes in an enterprise repository.
```

The full source file lives at `skills/sdlc/base/skill.yaml`.

## 2. Apply The Overlay

The payments overlay inherits the base and patches only the approved Markdown block.

```yaml
# /skills/sdlc/payments/kustomization.yaml
resources:
  - ../../base

namePrefix: payments-

patches:
  - path: patch-testing.yaml
    target:
      group: skills.agent.dev
      version: v1alpha1
      kind: Skill
      name: enterprise-sdlc
```

```yaml
# /skills/sdlc/payments/patch-testing.yaml
- op: replace
  path: /spec/blocks/2/markdown
  value: |
    ## Testing

    Run `make test-payments` after modifying payment service code. Include the command and result in the final response.
```

## 3. Render And Check

<Steps>

1. Render the overlay.

   ```bash
   # /scripts/build-skill.sh
   kustomize build skills/sdlc/payments > build/rendered/payments-sdlc.yaml
   ```

2. Verify the rendered resource against policy.

   ```bash
   # /scripts/build-skill.sh
   skillc verify \
     --policy policies/enterprise-sdlc.yaml \
     build/rendered/payments-sdlc.yaml
   ```

3. Compile the verified resource into a flat agent skill.

   ```bash
   # /scripts/build-skill.sh
   skillc compile \
     --out build/skills \
     build/rendered/payments-sdlc.yaml
   ```

4. Emit or attach the AIBOM when the agent run completes.

   ```bash
   # /scripts/build-skill.sh
   skillc aibom emit \
     --subject github.com/acme/payments@7a91d3f4 \
     --out runs/PAY-1842/aibom.json
   ```

</Steps>

`skillc` is the reference CLI name in this proposal. The repository includes representative outputs, not a finished compiler implementation.

## 4. Inspect The Rendered Source

The rendered object is still Markdown source, just composed and patched.

```yaml
# /build/rendered/payments-sdlc.yaml
apiVersion: skills.agent.dev/v1alpha1
kind: Skill
metadata:
  name: payments-enterprise-sdlc
spec:
  blocks:
    - id: testing
      markdown: |
        ## Testing

        Run `make test-payments` after modifying payment service code.
    - id: security-review
    - id: run-record
```

## 5. Inspect The AIBOM

The AIBOM records ancestry and activation.

```jsonc
// /runs/PAY-1842/aibom.json
{
  "resolvedSkills": [
    {
      "name": "enterprise-sdlc",
      "relationship": "base"

    {
      "name": "payments-enterprise-sdlc",
      "relationship": "overlay"
    },
    {
      "name": "payments-enterprise-sdlc",
      "relationship": "compiled-skill"
    }
  ],
  "activatedSkills": [
    {
      "name": "payments-enterprise-sdlc"
    }
  ]
}
```

## Success Criteria

The example is valid only if all of these are true:

- The overlay renders with Kustomize.
- The final Markdown compiles to a normal `SKILL.md`.
- The test command matches an approved command pattern.
- `security-review` and `run-record` remain locked.
- The AIBOM lists the base, overlay, compiled skill, checks, and activation record.
